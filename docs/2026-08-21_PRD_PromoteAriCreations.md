# PRD — Promote Ari's Creations (the shape library)

**Owner ask (2026-08-20):** when asked which reuse mechanism to build, the owner chose
*"Promote good creations from real games — when Ari builds something good procedurally in a
real child's game, capture that code into a reviewed library it can call later."*

**Status:** DRAFT. Nothing built. This document exists to be argued with before code.

---

## 1. Problem

**Nothing Ari builds is ever reused.** Verified against the code, 2026-08-21:

- The asset library is **build-time only**. `manifest.json` is generated by
  `scripts/vendor-*.mjs` on the dev Mac and bundled into the app. Nothing under `src/`
  writes to it, and nothing uploads to the asset host at runtime.
- There is no recipe store, no snippet library, no promotion path. The greps come back empty.

So when Ari builds a bird out of `BoxGeometry` and `SphereGeometry`, that code lives in **that
one game's HTML and nowhere else**. The next child asking for a bird gets a fresh attempt that
may be better or worse. Two children asking on the same day get two unrelated birds, and
neither is kept.

### 1.1 Why this is urgent now, not theoretical

The 2026-08-21 bird retirement removed the only `bird` model from the offer set on the
explicit reasoning that *"the successor is a bird Ari builds in code."* That successor is
re-derived from scratch on every single turn. **The library has a hole, and the thing we said
would fill it does not persist.** The same is true for anything the 322-model library lacks.

### 1.2 What "good" looks like when it happens

The evidence that Ari CAN build good geometry is in the games themselves — the AutoRicksaw
city (1,250 draws/frame of hand-built scenery), the Delhi skyline. These are real, they
rendered, and every one of them is stranded.

## 2. What gets promoted — code, not meshes

**A promoted artefact is a `.js` builder function, not a `.glb`.** Decided on constraints, not
taste:

| Approach | Why not |
|---|---|
| Export Ari's mesh to GLB at runtime and upload | The asset host is **append-only** — every upload is permanent and unreviewable after the fact. Needs storage, dedup, and a moderation queue before a single byte lands. Rejected for v1. |
| Hand-author recipes ourselves | That is us creating, not Ari. Does not answer the ask, and does not scale. |
| **Capture the builder function from a real game** | The code already exists, already ran, already rendered in a real browser. Reviewable as text. Zero new storage. **Chosen.** |

A recipe is a self-contained function that takes no game state and returns a `Group`:

```js
// shape: bird — promoted from game <slug>, reviewed <date>
export function build(THREE) { /* returns a Group, no globals, no side effects */ }
```

## 3. Where candidates come from — and the boundary that matters

**Source: PUBLISHED games on the Ariantra platform. Never the Ari chat database.**

This is the single most important design decision in this document, and it is what makes the
feature buildable at all.

- Published games are already public (the catalog), already passed a publish step, and are
  readable from S3 by game id and version — the exact path
  `Ariantra-Platform/scripts/model-usage.ts` already walks.
- The Ari-side SQLite DB holds **children's chat transcripts** and is off-limits by policy.
  A pipeline that read it would be unbuildable and unreviewable.

Reading only published bundles sidesteps the child-data boundary completely. **No transcript
is ever touched.**

### 3.1 Ownership — settled by the published terms, not by assumption

`Ariantra AI/terms.html` §06, *Game Ownership & Intellectual Property*:

> "All games and code built on the Ariantra platform are owned by Ariantra AI Foundry Private
> Limited… Ariantra may publish, modify, distribute, and monetize any game built during
> sessions… **Game concepts and ideas may be shared with and developed by other Ariantra
> students as part of the learning programme.**"

Promotion is squarely inside what parents already agreed to. The last clause describes this
feature almost exactly.

### 3.2 The two obligations that DO apply

1. **Scrub personal data before promotion.** A game's source can carry a child's first name in
   a comment, a credit string, a window title, a high-score label. A recipe must ship with
   none of it. Automated strip + a human read, both required. The DPDP purpose-limitation
   framing in the terms ("strictly to deliver our service") is satisfied by a shape recipe; a
   child's *name* riding inside one is not.
2. **Content standards carry over** (terms §07). A promoted shape inherits the 8–14 bar. A
   review that only asks "does it look good" is not enough.

## 4. Tech Feasibility

Every stage below is a mechanism that **already exists and is already load-bearing** somewhere
in these two repos. Nothing here needs a new capability.

| Stage needs | Does it exist? | Precedent |
|---|---|---|
| Read every published game's source | **Yes** | `Ariantra-Platform/scripts/model-usage.ts` already walks `bundles/<id>/<version>/index.html` out of S3 for all 144 rows |
| Run a shape headless and screenshot it | **Yes** | `scripts/render-assets.mjs` renders published assets through the real vendored three + GLTFLoader, top-down and 3/4 |
| Prove a shape actually renders, not just parses | **Yes** | `scripts/verify-game-html.mjs`, plus the pixel-census approach that caught the 2026-08-20 blue screen |
| Offer a named thing to Ari, genre-aware and capped | **Yes** | `asset-taxonomy.ts` + `selectModelNames` + the genre spread, `PROMPT_MODEL_CAP = 30` |
| Inject a runtime global into a game | **Yes** | `runtime-helpers.ts` `loadModelHelper()` — versioned global, idempotent, `window.__arLoadModelVersion` |
| Withdraw something that turns out bad | **Yes** | `retired.ts` (2026-08-21) — resolvable, never offered |
| Review a batch by eye before it ships | **Yes** | the 2026-08-08 asset-fitness contact-sheet flow |

### 4.1 The one genuinely new piece

**Extracting a self-contained builder from a game's source.** This is a static-analysis
problem on generated JS, and it is the only part with real uncertainty. Two things make it
tractable:

- The generated games speak a **narrow, taught dialect** — `prompt-catalog.ts` teaches a
  curated import list (`CURATED_IMPORT_NAMES`), so the vocabulary a shape can be built from is
  known in advance and small.
- We do not need to extract *every* shape. A harvester that finds only the cleanly-separable
  ones is fine; a missed candidate costs nothing.

**Risk:** the model may build geometry inline in `animate()` rather than in a named function,
in which case there is nothing separable to lift. This is exactly what Build-order step 1
measures before any of the rest is built.

## 5. How a promoted recipe reaches Ari

**It becomes a first-class entry in the library it already knows**, with `type: 'recipe'`
instead of `type: 'model'`. That reuses every mechanism already built and tested:

- **`asset-taxonomy.ts`** — genre + tags, so retrieval finds it the same way it finds `dog`.
- **`selectModelNames` / `retrievedModelNames`** — the same capped, genre-spread retrieval,
  so a recipe costs the prompt exactly what a model name costs, and `PROMPT_MODEL_CAP = 30`
  still holds.
- **`inject.ts`** — a game that names a recipe gets the builder injected as a runtime global,
  the same shape as `loadModel`: `window.arShape('bird')` returns a `Group`.
- **`retired.ts`** — a recipe that turns out badly gets retired, not deleted, with the
  resolvable-but-never-offered guarantee already in place.

**Delivery is a runtime global, not prompt text.** Pasting the function body into the prompt
would cost hundreds of tokens per shape and put the code inside the cached prefix. Injecting it
costs the prompt one name.

### 5.1 The rule that keeps this from becoming a ceiling

**A recipe is offered, never mandated.** If the prompt says "use `arShape('bird')` for birds",
Ari stops trying, and the library's best bird becomes its only bird — permanently. The catalog
must present a recipe as *available*, exactly like a model, and Ari must remain free to build
something better. **The next promotion comes from Ari beating the recipe**, which cannot happen
if it is forbidden from trying.

## 6. The pipeline

### Stage 1 — Harvest (deterministic, no LLM)
Walk published bundles from S3 (`model-usage.ts`'s reader). Extract top-level functions that:
build geometry from curated `three` primitives; reference no globals beyond `THREE`; touch no
DOM, network, audio, or game state; and return a `Group`. Anything else is not a shape.

### Stage 2 — Score (deterministic)
Rank candidates by signals we already hold: the game is **published** (a human shipped it), its
**play count** (`playsReal`), its **likes**, and mesh complexity within a sane band — a shape
made of 2 boxes is not worth a library slot, and one of 400 will not fit the first-load budget.

### Stage 3 — Render (the instrument, no LLM)
Run the extracted function headless and screenshot it, reusing `render-assets.mjs`'s exact
mechanism — same vendored three, same loader path, same top-down + 3/4 framing. **This is
non-negotiable**: the 2026-08-08 asset-fitness PRD already established that "the only
instrument that answers it is an eye", and the 2026-08-20 injector bug proved that a thing can
be error-free and still render nothing.

### Stage 4 — Review (human, blocking)
A contact sheet, exactly like the first-party model audit. The reviewer answers three
questions, all of which must pass: **Does it look good? Is it free of personal data? Does it
meet the content standard?** Nothing is promoted without this.

### Stage 5 — Publish
Add the recipe to the manifest + taxonomy, commit it. It is code in the repo, versioned in git
— reviewable in a diff, revertable, no permanent append-only upload.

## 7. Use Cases (all of them, with how we tackle each)

| # | Case | How it is handled |
|---|---|---|
| U1 | Child asks for a bird; a promoted `bird` recipe exists | Retrieval offers the name like any model; Ari may call `arShape('bird')` **or** build its own (§5.1) |
| U2 | Child asks for a bird; no recipe yet | Exactly today's behaviour — Ari builds from primitives. No regression |
| U3 | Child asks for something a rigged MESH covers better (a dog) | Models and recipes sit in the same retrieval set; the mesh wins because it animates. Recipes never shadow a model |
| U4 | A promoted recipe turns out to look bad in real games | `retired.ts` — retire it. Existing games keep resolving it; nobody new is offered it |
| U5 | A recipe and a model would share a name | Rejected at promotion: names are unique across the manifest, enforced by the existing contract test |
| U6 | The source game is later deleted or unpublished | Irrelevant — the recipe is code committed to this repo, not a reference to that game |
| U7 | A candidate carries a child's name in a comment or a string | Scrubbed automatically, then read by a human. Both required (§3.2) |
| U8 | A candidate violates the content standard | Blocking question in the Stage-4 review, alongside "does it look good" (terms §07) |
| U9 | Ari builds something BETTER than the existing recipe | The next promotion candidate. This is the intended loop, and it only works because §5.1 leaves Ari free to try |
| U10 | Too many recipes crowd models out of the prompt | `PROMPT_MODEL_CAP` already bounds the offer set; the ceiling and its trigger are in §8 |
| U11 | A recipe throws at play time in some game | Same class as any bad asset: caught by the render gate before promotion, and retirable after |
| U12 | Harvest finds nothing worth promoting | The PRD is answered "no" for the cost of one read-only script. This is a real and acceptable outcome (§10 step 1) |

## 8. Scale ceilings (CLAUDE.md rule 8)

| Limit | Ceiling | Trigger to revisit |
|---|---|---|
| Prompt budget | `PROMPT_MODEL_CAP = 30` names/turn, shared with 318 models | Recipes crowding models out of retrieval |
| First-load budget | 2 MB/game (`FIRST_LOAD_BUDGET_BYTES`); each injected recipe is inline JS | A game naming many recipes at once |
| Review throughput | One human, one contact sheet | More than ~20 candidates per batch |
| Harvest cost | Full S3 walk of every published bundle | Beyond ~1,000 games; then harvest incrementally by `updatedAt` |

## 9. Open decisions — owner's call, needed before build

1. **Review gate.** One reviewer (you), or a second pair of eyes for the content-standard
   check? Recommendation: you alone at this volume, revisit at ~20/batch.
2. **Attribution.** Promoted from a specific child's game. Do we credit them ("shape by
   Agilan, 10"), and does that re-introduce the personal data we just scrubbed? Recommendation:
   credit in the **repo comment** (internal, not shipped), never in the served game.
3. **Revenue Programme.** Terms §06 promises a revenue share when a game generates revenue. If
   one child's bird ends up in 200 games, is that in scope? Genuinely unclear, and better
   decided now than after it happens.
4. **Does a recipe ever replace a model?** If Ari's bird beats a vendored bird, do we retire
   the mesh? Recommendation: yes — `retired.ts` already makes that safe.

---

## 10. Build order

1. Harvest + score (Stages 1–2), read-only, prints a candidate list. **Cheap, and it
   immediately answers "is there anything worth promoting?"** — which could kill this PRD.
2. Render + contact sheet (Stage 3–4).
3. `type: 'recipe'` through manifest → taxonomy → retrieval → inject (Stage 5), test-first.
4. Promote **one** shape end-to-end. A bird, since we owe the library one.

**Step 1 is deliberately the whole risk.** If a harvest over every published game turns up no
self-contained builder worth keeping, this feature is not worth building, and we will know that
for the cost of one read-only script.

---

## 11. What could make this a bad idea

Stated plainly, so it is not discovered late:

- **Ari's procedural shapes may simply not be good enough to promote.** The first-party model
  audit found our own hand-authored models were the weakest in the library. Code-built shapes
  could be worse than what we already reject. Step 1 tests this before anything is built.
- **A promoted recipe has no skeleton.** It cannot be skeletally animated, ever. For creatures
  — the very gap the bird retirement opened — a recipe is a *worse* answer than a rigged mesh.
  Recipes are best for scenery, props, and vehicles; for animals, sourcing a rigged CC0 mesh
  remains the better fix.
- **It puts a ceiling under Ari** if the offer rule in §5.1 is not held to.
