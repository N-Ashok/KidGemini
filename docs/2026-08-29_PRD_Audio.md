# PRD — Audio: 93% of kids' games are silent

2026-08-29 · Status: **BUILT + MEASURED locally (§9) — not deployed.** Owner: Ashok. Started on owner
instruction 2026-08-29 ("the audio is very minimum… awkward audio on a good
gameplay is a broken game… for the game in play music is not there").

Companion docs: `2026-08-29_PRD_GameFeelAndMotivation.md` (deferred; a turbo
boost needs shake and particles as well as a whoosh), `PROMPT_MANAGEMENT.md`
(§2.3 audio section), `assets/runtime-helpers.ts` (`playSound`/`playMusic` —
injected at delivery, so Phase 2 retrofits games that already exist),
`COST_TOKEN_BUDGET.md`.

## 0. One-paragraph summary

We ship 28 sound effects and 7 music loops, and 93% of real games play in
silence. The cause is not the library and not the model — it is the gate:
audio guidance is unlocked only when the child types "sound", "music", "song"
or "sfx". A child who asks for a racing game, a jumping game, or a turbo boost
is never told the sounds exist. This PRD widens that gate, rewrites the
playbook so the model knows *which* sound belongs to *which* event (the
"awkward audio" class), insists on background music, and fixes two things the
prompt cannot reach: `playSound` has no pitch variation and no spam guard.

## 1. Baseline — measured 2026-08-29 (prod DB, aggregate only)

Latest artifact of the 237 most recent conversations that contain a game:

| | count | share |
|---|---|---|
| Games with **any** audio (`playSound`/`playMusic`) | 23 | **10%** |
| Games with **background music** (`playMusic`) | 17 | **7%** |
| Games with sfx but no music | 6 | 3% |
| Distinct `playSound` call-sites, among games that have sfx | 3.7 avg | — |

**Library, for contrast:** 28 sfx (`jump, coin_pickup, hit, explosion, click,
powerup, game_over, win, laser, whoosh, confirm, error, back, select, toggle,
open_menu, close_menu, drop, scroll, question, pop, zap, footstep, door_open,
door_close, coins, page_turn, chop`) and 7 music loops (`bg_loop_upbeat,
bg_loop_chill, jingle_win, bg_loop_playful, bg_loop_dreamy, bg_loop_gentle,
bg_loop_swing`). None of it is reachable unless the gate opens.

## 2. Root cause

`AUDIO_TRIGGER = /\b(sounds?|music|songs?|sfx)\b/i` in `assets/catalog-gate.ts`,
mirrored by the edit-side gate. Measured against real asks:

```
build audio=false  edit audio=false   "add a turbo boost power-up that makes the car go fast"
build audio=false  edit audio=false   "make a racing game"
build audio=false  edit audio=false   "make a jumping game with 20 levels"
build audio=false  edit audio=false   "add a boss on level 3"
build audio=true   edit audio=true    "make a racing game with sound"      ← only this
```

**The owner's turbo boost received no audio guidance at all.** Combined with
the absence of a juice playbook (no shake, no speed lines, no particles), a
turbo boost is a number going up — hence "pathetic".

Three further defects, confirmed against external sound-design guidance:

- **No event→sound map.** The playbook lists 28 names and never says which fits
  which event, nor which music suits which mood. Mismatched audio "breaks the
  player's connection… creating a jarring experience" — the owner's "awkward
  audio on a good gameplay is a broken game".
- **No variation → ear fatigue.** Best practice is never to reuse one file for
  a frequent action (vary pitch ±10%, volume ±3 dB). `window.playSound(name)`
  accepts **no** pitch or volume argument, so a jump sound plays identically
  200 times. Not fixable from the prompt.
- **No spam guard.** `playSound` connects straight to `destination` at full
  gain with no minimum interval, so ten collisions in one frame stack ten
  copies → clipping. Also not fixable from the prompt. (Music is already
  mixed correctly beneath sfx at gain 0.5.)

## 3. Goals / non-goals

**Goals.** Most games have sound AND background music by default; sounds match
their events; repeated sounds do not fatigue; simultaneous sounds do not clip.

**Non-goals.** New audio assets (the library is adequate). Positional/3D audio.
Adaptive music that reacts to tension — noted as a future item, not now.
Juice/shake/particles — `2026-08-29_PRD_GameFeelAndMotivation.md`.

## 4. Design

### Phase 1 — the gate (prompt only, the 93% fix)

Audio unlocks on **any game-build turn**, not on keywords. Rationale: a silent
game is a worse default than the playbook's tokens, and the measured cost is
~+$0.00037 per build (~+0.9%; the section is 488 tokens, not the ~250 first
estimated).

**Correction found by measurement (§9.2).** The first cut left the EDIT gate
keyword-only, on the reasoning that "an ordinary edit is unaffected". That was
wrong, and it left the owner's actual bug unfixed: *"add a turbo boost
power-up"* is an EDIT, so the re-run still came back with **no music and zero
sound effects**. Nobody says "add a turbo boost **with sound**". The edit gate
therefore also fires on **gameplay EVENT words** — boost/turbo/power-up, jump,
shoot/laser/gun, explode, crash, collect/coins/pickup, collision, win, lose,
game over — because an edit that introduces a new event needs that event's
sound. `button`/`menu`/`score`/`goal` were deliberately excluded after a test
caught "add a reset button" pulling in the whole 488-token playbook for one
click; UI clicks are covered on the build turn instead. A cosmetic edit
(colour, size, layout) still gets nothing.

### Phase 2 — the playbook rewrite (prompt only, the "awkward audio" fix)

- **Directive, not permissive.** Today: "you may add professional sound
  effects". Becomes: every action game gets sound, and **background music
  starts once when play begins** — the owner's explicit complaint.
- **Event→sound map**, so the model stops guessing: jump→`jump`,
  collect→`coin_pickup`/`coins`, hit→`hit`, explode→`explosion`,
  power-up/boost→`powerup`+`whoosh`, shoot→`laser`, win→`win` or `jingle_win`,
  lose→`game_over`, button→`click`, menu→`open_menu`/`close_menu`.
- **Music→mood map**: `bg_loop_upbeat` racing/action, `bg_loop_playful`
  platformer/arcade, `bg_loop_chill`/`bg_loop_gentle` puzzle/quiz,
  `bg_loop_dreamy` exploration, `bg_loop_swing` comedy.
- **Silence is a bug for the big three moments**: start, win, lose.

### Phase 3 — the runtime helper (code, retrofits existing games)

`window.playSound(name, opts?)` where `opts = { pitch, volume }`:
- default **±10% random pitch jitter** on every call, so repetition varies
  without the game asking;
- `volume` via a gain node (sfx default 1.0, music stays 0.5);
- **min-interval guard** per sound name (~50 ms) so a burst cannot stack;
- backward compatible — `playSound("jump")` keeps working, and because the
  runtime is injected at delivery, **games that already exist get this for
  free** on their next render.

## 5. Testing (test-first)

- Gate: a plain "make a racing game" now unlocks audio on a build turn; the
  edit gate is unchanged; quiz/board games still get audio (they have buttons)
  but must not get action-only guidance.
- Playbook: pins for the event→sound map, the music-on-start rule, and the
  mood map; token ceiling; constant-with-no-interpolation (cache contract).
- Runtime: `playSound` called twice produces different playbackRate values
  inside ±10%; the same sound twice within the guard window plays once;
  `playSound(name)` with no opts still works; a failed load stays silent and
  never throws.
- **Behaviour, not strings** (rule 12): build real games for asks with no sound
  word ("make a racing game", "add a turbo boost"), assert the output contains
  `playMusic` and ≥3 distinct `playSound` names, and that it still runs in a
  browser.

## 9. Measurement log — 2026-08-29, local dev against the real model

### 9.1 Build turn, no sound word in the ask
`"make a racing game"` → **music `bg_loop_playful`, 7 distinct effects**
(whoosh, hit, coin_pickup, powerup, game_over, win, click). Baseline for this
class was silence. Sounds are correctly matched to their events; the one
imperfection is the mood pick — the map suggests `bg_loop_upbeat` for racing
and the model chose `bg_loop_playful`, which is defensible for a kids' game.

### 9.2 The owner's turbo boost, before and after the edit-gate fix
| | music | distinct sfx |
|---|---|---|
| after Phase 1 only (edit gate keyword-only) | **NONE** | **0** |
| after the event trigger | **`bg_loop_upbeat`** | **7** — explosion, coin_pickup, **powerup**, **whoosh**, jingle_win, confirm, game_over |

`powerup` + `whoosh` is exactly the boost mapping the playbook teaches. Edit
input cost 9,608 tokens vs ~8,073 for this game's edits without the playbook:
**+1,535 tok ≈ $0.0012 ≈ ₹0.10 per audio-bearing edit.**

### 9.3 Both games run clean in a browser (`verify-game-html.mjs`, 2/2).

### 9.4 What was NOT verified
Nobody has *listened* to a generated game. The pitch jitter, the burst guard
and the mixing are verified by executable unit tests against a fake WebAudio
context (`audio-runtime.test.ts` AR.1–AR.6), not by ear. Adoption in
production (§6) cannot be measured until this deploys.

## 6. Acceptance

Re-run the §1 query after a week of real traffic. Target: **any audio ≥70%**
and **music ≥60%** of new games, up from 10%/7%. Distinct sfx per game ≥5,
up from 3.7.

## 7. Decisions needed from the owner

1. **Should audio be on for EVERY build, or only action games?** Recommended:
   every build — a quiz still wants `click`, `confirm`, `error` and a gentle
   loop, and the cost is ~0.5%.
2. **Should background music auto-start, or wait for a mute/unmute toggle?**
   Recommended: auto-start with a visible 🔊/🔇 toggle, because browsers block
   audio until first interaction anyway and the game already has a start
   button.

## 8. What this does NOT do, and the ceilings

Does not add assets, positional audio, or adaptive/tension-driven music. Does
not fix the *juice* half of "pathetic" (separate PRD). The pitch jitter is a
crude stand-in for real sound families — with 28 files and one variation each,
a very repetitive action will still tire; the honest fix would be 3–5
recordings per common action, which is an asset-library change, not code.
